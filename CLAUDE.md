## Non-obvious invariants — easy to break, easy to miss

- **Ranked semantics everywhere.** Every preference list is ordered (rank 1 = top pick). No `Set`-shaped preferences anywhere in the schema or UI.
- **Balance equation must hold.** `podHeadCount = orchCount × podHeadsPerOrch` and `agentCount = podHeadCount × agentsPerPodHead`. The completion pass (`src/lib/matching/complete-match.ts`) relies on this — violating it breaks coverage. The admin EventConfig editor surfaces a warning when broken.
- **Determinism.** Auto-fill RNG seed is `"ai-unlimited-" + matchType + "-" + currentRunId` (see `src/lib/matching/rng.ts`). All tie-breaks sort by id ASC. Same inputs → identical outputs.
- **`EventConfig` is a singleton.** Only id=1 exists; enforced in application code (`src/lib/config.ts`), not by the DB.
- **Resident-proposing direction.** Run 1: Pod Heads propose to Orchs. Run 2: Agents propose to Pod Heads. Proposing side is resident-optimal — do not flip.
- **Project FCFS ordering.** Sort by `preferencesSubmittedAt ASC NULLS LAST, id ASC`. Auto-filled (null) Pod Heads go *last*.
- **`autoGenerated=true` is load-bearing.** Auto-filled rows are flagged; the transparency UI reads this to show "Auto-assigned" badges (`src/lib/results.ts`). Set it on every row written by auto-fill in `matching-service.ts`.
- **Matching engine is pure TS.** Lives in `src/lib/matching/`. No Prisma imports — testable in isolation against §14.2 cases. The DB bridge lives in `src/lib/matching-service.ts`.
- **Drafts vs finalized.** Matching runs write to `MatchingRun` only. `assignedOrchId` / `assignedPodHeadId` / project assignment columns are written **only on `finalizeMatch`**. Re-run before finalize replaces draft; after finalize requires explicit `rollbackMatch`.
- **PodHeadProjectPick is wipe+replaced on PROJECT_ASSIGNMENT finalize.** The algorithm can assign a balance-fallback project that wasn't in the user's original picks — the picks rows are wiped and re-inserted to reflect the actual assignment. Original picks + dispositions remain captured in `MatchingRun.stats` for the transparency UI.
- **Phase-gated writes.** `EventConfig`, user import, and project CRUD are editable only during `REGISTRATION` (§5.3). Profile edits and preference submission require `PREFERENCES` *and* a completed profile.
- **`requireAuth()` re-reads `profileCompletedAt` / `role` / `isAdmin` from the DB** on every protected page (`src/lib/permissions.ts`). The JWT freezes those at sign-in time, so trusting it would loop users back to `/profile-setup` right after they save. Don't "optimize" this away.
- **Server-action files must export only async functions.** `"use server"` files cannot export constants/objects (only `type`s). Stash any non-function exports in a sibling `types.ts`. (We hit this once already with `initialImportState` in `src/app/admin/users/`.)

## Matching engine (`src/lib/matching/`)

Pure TS, no Prisma imports. Each module independently testable:

- `types.ts` — shared contract
- `rng.ts` — seeded mulberry32 + shuffle + sample
- `hospital-residents.ts` — resident-proposing Gale-Shapley (SRS §7.3)
- `complete-match.ts` — straggler placement (§7.4)
- `project-assignment.ts` — FCFS + caps + balancing (§7.5)
- `auto-fill.ts` — deterministic non-submitter prefs (§7.2)
- `index.ts` — public API

The DB bridge in `matching-service.ts` is the ONLY place that calls into both the engine and Prisma. Keep it that way.

Tests skip integration suites when `DATABASE_URL` is unset, so `npm test` works in CI without a DB.

## Out of scope for v1 (SRS §1.2)

Do not build (the SRS explicitly excludes these):
- Email / Slack notifications
- Opt-out flow for role designations
- Forbidden-pairing constraints
- Multi-event or multi-language support
- Public / external participant access
- Manual override UI (FR-A7) — deferred from Phase 7; service layer doesn't support it yet
